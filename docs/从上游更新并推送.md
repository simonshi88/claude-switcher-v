# 从上游更新并推送到自己的仓库

> 仓库：`D:\code\claude-switcher`
> 上游：`https://github.com/YOURSJEYO/claude-switcher.git`（remote `upstream`）
> 自己的：`https://github.com/simonshi88/claude-switcher-v.git`（remote `origin`）

## 1. 分支模型

| 分支 | 内容 | 能否直接提交自定义改动 |
| --- | --- | --- |
| `main` | **上游镜像**，只跟随 `upstream` | ❌ 不要 |
| `custom/v-ninja` | 上游基线 + 1 个自定义提交（适配补丁 + tools + docs） | ✅ 全部自定义改动在这里，由脚本重建 |

这样升级时 **不需要解决合并冲突**：每次把 `custom/v-ninja` 重建到新 tag 上，重新施加规则表即可；`main` 永远干净，可随时和上游对比。

## 2. 一条命令更新

```powershell
# 在仓库根目录
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\update-from-upstream.ps1
```

默认行为：

1. `git fetch upstream --tags`
2. 选目标：最新的 `v*` tag（当前 `v1.10.0`）；也可 `-Ref upstream/main` 跟主线
3. `main` 重置到该 tag 并推送（`--force-with-lease`）
4. 暂存自定义文件（`tools/`、`docs/` 里我们新增的），重建 `custom/v-ninja`
5. 依次跑 `tools/apply_vninja.py`（mac 44 条）和 `tools/apply_vninja_windows.ps1`（windows 46 条）
6. 校验两个执行器 `-Check`：必须 0 待应用、0 失败
7. 提交 `custom: Clash V-Ninja 适配（<tag>）` 并推送 `custom/v-ninja`

常用参数：

| 参数 | 作用 |
| --- | --- |
| `-Ref v1.10.0` / `-Ref upstream/main` | 指定目标（默认最新 tag） |
| `-Branch custom/v-ninja` | 自定义分支名（默认） |
| `-BaseBranch main` | 上游镜像分支名（默认） |
| `-NoPush` | 只本地提交，不推送 |
| `-DryRun` | 只重置/打补丁/校验，不提交不推送 |
| `-SkipFetch` | 不 fetch（离线/测试） |

## 3. 前置条件

- **代理**：本机 git 全局 `http.proxy=http://127.0.0.1:7890`，GitHub 直连不通；先启动 Clash V-Ninja（`D:\Clash V-Ninja\clash-ninja.exe`），等 7890 端口起来。
- **工作区干净**：脚本会 `git checkout -B` 重置分支；已跟踪文件有未提交改动时会直接拒绝。
- **tools/ 和 docs/ 必须在自定义分支里**：脚本靠它们打补丁；首次从上游新建仓库时，先从旧仓库/旧分支复制这两个目录。

## 4. 规则失败怎么办

脚本会在失败处停下，并且 **不提交**。按 id 对照：

- mac：`docs/新增代理客户端适配规范.md` 第 2 节（规则表）
- windows：`docs/Windows-自定义适配与升级.md` 第 2 节（规则表）
- 规则文件：`tools/vninja-patch.json` / `tools/vninja-patch-windows.json`

改法：找到上游新代码 → 更新对应规则的 `old` / `new`（或新增一条）→ 重新运行脚本。

## 5. 手工流程（与脚本等价，排障用）

```powershell
git fetch upstream --tags

# 1) main 镜像上游
git checkout -B main v1.11.0
git push --force-with-lease origin main

# 2) 重建自定义分支（tools/docs 来自旧的自定义分支）
git checkout -B custom/v-ninja v1.11.0
git checkout custom/v-ninja@{1} -- tools docs   # 取上一次自定义提交里的 tools/docs
python tools\apply_vninja.py
powershell -File tools\apply_vninja_windows.ps1

# 3) 校验
python tools\apply_vninja.py --check
powershell -File tools\apply_vninja_windows.ps1 -Check

# 4) 提交并推送
git add -A
git commit -m "custom: Clash V-Ninja 适配（v1.11.0）"
git push --force-with-lease origin custom/v-ninja
```

> `custom/v-ninja@{1}` 指这个分支上一次的位置；如果已经 reset 过，用 `git reflog` 找旧提交。

## 6. 更新后装到本机

```powershell
powershell -File .\tools\deploy_vninja.ps1            # 保留本机配置，替换脚本
powershell -File .\tools\deploy_vninja.ps1 -Group "🚀 节点选择"
```

系统级设置（锁时区 / 关 IPv6 / 重注册计划任务）仍需管理员，见 `docs/Windows-自定义适配与升级.md` 第 5 节。

## 7. 注意

- **不要把自定义改动提交到 `main`**，否则下次脚本重置会丢；所有改动写进 `tools/` 的规则表或执行器。
- 补丁生成的 `*.vninja.bak` 已在 `.gitignore` 里；需要回退用 `git checkout` 对应基线。
- `custom/v-ninja` 每次重建后是新的 commit，历史里看不到逐次升级的 diff；需要记录版本时看 commit message 里的 tag。
- 推送用 `--force-with-lease`：只有远端没有别人新提交时才覆盖；冲突时先 `git fetch origin` 看看。

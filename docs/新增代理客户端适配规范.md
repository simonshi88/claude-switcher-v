# 新增代理客户端适配规范（以 Clash V-Ninja 为例）

> **基准版本：上游 1.10.0（2026-11-22 迁移）。**
> 1.10.0 新增 `bettbox` 客户端与若干检查项；本文涉及模式列表 / 安装器菜单的锚点已同步为 1.10.0 原文。
> 规则表 `tools/vninja-patch.json`（44 条）是权威：升级时先跑 `python tools/apply_vninja.py`，
> 失败项再按本文第 7 节对照。Windows 侧对应 `tools/apply_vninja_windows.ps1`（46 条）。

> 适用场景：要接入一个新的代理客户端（如某个 Clash 的 fork），而不是把上游代码改造成这个客户端。
>
> **核心原则：一个客户端 = 一个 `PROXY_MODE`。上游分支（`clash-verge`）一个字节都不改。**
> 这样上游发新版时，`diff` 里只会看到"新增的行"，不会出现反复冲突，也不需要在每次升级后重新打补丁。

> 仓库分支模型（main 跟上游 / custom/v-ninja 放适配）与更新命令见 [从上游更新并推送.md](从上游更新并推送.md)。

## 0. 为什么不再用"改名"

之前走的是"把 Clash Verge 的名字/目录替换成 fork 的名字"这条路。结果每次上游升级，1.8.0 又变回 `verge-mihomo`、`("clash-verge.yaml","verge.yaml")`，就得重新改一遍，而且很容易漏（漏了 `proxy_alive` 就会显示"代理未运行"，还可能触发保镖误杀 Claude）。

改成"新增模式"后：上游代码不动，fork 只是多一个分支。

## 2. 每个触点怎么写

### 2.1 配置目录（派生，不要写死）

```bash
clash_dir_for_mode() {
    case "$1" in
        v-ninja) echo "$HOME/Library/Application Support/io.github.clash-verge-ninja.clash-verge-ninja" ;;
        *)       echo "$HOME/Library/Application Support/io.github.clash-verge-rev.clash-verge-rev" ;;
    esac
}
CLASH_DIR="$(clash_dir_for_mode "$PROXY_MODE")"
```

关键：目录由模式派生，**安装器不要再往脚本里 sed 一个固定目录**，否则 `set-client` 切换后会指向错的目录。
`set_client()` 里切换模式后要同步重算：`CLASH_DIR="$(clash_dir_for_mode "$PROXY_MODE")"`。

### 2.2 名称与进程

```bash
proxy_name:      v-ninja)      echo "Clash V-Ninja" ;;
proxy_app_name:  v-ninja)      echo "Clash V-Ninja" ;;
proxy_alive:     v-ninja)      clash_core_up ;;
```

`clash_core_up()` 目前是两种内核名都认：

```bash
clash_core_up() { pgrep -x ninja-mihomo >/dev/null 2>&1 || pgrep -f '[v]erge-mihomo' >/dev/null 2>&1; }
```

接入新 fork 时先确认真实内核名：`ps -Ao comm | grep -i mihomo`，再加一条 `pgrep -x <binary>`。
`[v]` 的写法是为了避免 `pgrep -f` 匹配到 pgrep 自己的命令行。

### 2.3 Clash 系流程开关

```bash
is_clash_mode() { case "$PROXY_MODE" in clash-verge|v-ninja) return 0 ;; *) return 1 ;; esac; }
```

原来所有 `[ "$PROXY_MODE" = "clash-verge" ]` 的判定都改成 `is_clash_mode`（`checkdetail`、`webrtc_status`、`fix`、写入全局脚本、全局模式判断）。
新增 Clash 系客户端时，只需往这个函数里加名字。

### 2.4 控制接口候选文件

不同 fork 的运行时配置文件名不同：Clash Verge 是 `clash-verge.yaml`，V-Ninja 是 `config.yaml`。

```python
CLIENT_MODE = os.environ.get("CLASH_CLIENT_MODE", "clash-verge")
...
names = (("clash-verge.yaml", "config.yaml", "verge.yaml")
         if CLIENT_MODE == "v-ninja" else ("clash-verge.yaml", "verge.yaml"))
```

bash 侧通过 `clash_rules()` 传环境变量：`CLASH_CLIENT_MODE="$PROXY_MODE" ...`。
上游分支的候选列表保持原样，不要为了兼容而全局放开。

### 2.5 安装器

- **识别顺序**：V-Ninja 目录 → Clash Verge 目录 → FlClash → Shadowrocket → 手动选择菜单（`9) v-ninja`）
- **组名来源**：`clash_config_yaml()` —— V-Ninja 读 `profiles.yaml` 里 `current:` 指向的订阅文件（组在订阅里）；Clash Verge 读 `clash-verge.yaml`
- **组名解析**：用内嵌 `python3`，兼容两种 YAML 写法（`- name: X` 内联 / `-` 换行 `name: X`）
- **重启客户端**：用 `$CLIENT_NAME`，不要写死字符串

```bash
case "$MODE" in
    v-ninja)      CLIENT_NAME="Clash V-Ninja" ;;
    clash-verge)  CLIENT_NAME="Clash Verge" ;;
    *)            CLIENT_NAME="$MODE" ;;
esac
```

### 2.6 root 保镖

```bash
case "$MODE" in
    clash-verge) pgrep -f '[v]erge-mihomo' >/dev/null 2>&1 || ok=0 ;;
    v-ninja)     pgrep -x ninja-mihomo >/dev/null 2>&1 || ok=0 ;;
```

保镖脚本是 root 所有、`MODE` 在安装时写死。改完模板必须重新装一次（安装器，或单独用管理员权限覆盖），否则 `checkdetail` 会报保镖模式不一致。

### 2.7 App 下拉菜单

```swift
("clash-verge", "Clash Verge"),
("v-ninja", "Clash V-Ninja"),
```

`clientChoices` 同时用于校验 `set-client` 的入参，加进去即可，无需改其他逻辑。

## 5. 常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `代理内核=fail:...未运行` | `proxy_alive` 只认上游内核名 | 补 `pgrep -x <fork内核名>` |
| `未找到本机 Clash 控制接口` | 候选配置文件名不含该 fork 的运行时配置 | 在对应模式的候选列表里加 |
| `运行规则未按策略置顶` | 旧版把规则写进了 profile 级增强文件（`prepend`），排在 `Script.js` 之前 | `grep -rl "intercomassets.com" profiles/` 找到并清空（先备份），再重启客户端 |
| 保镖把 Claude 杀了 | 保镖 `MODE` 与核心 `PROXY_MODE` 不一致，或内核名写错 | 重新装保镖；确认 `grep '^MODE='` 与当前模式一致 |
| `pgrep` 匹配到自己 | 用了 `pgrep -f 关键词` | 写成 `pgrep -f '[关]键词'` |
| 升级后又要改一遍 | 把 fork 名字改进了上游分支 | 改用本规范：新增模式，不动上游 |

## 6. 接入另一个 fork 时的探测命令

第 5 条的替换内容（组名来源 + 解析）：

```bash
# Clash 系客户端的组名来源:Clash Verge 读 clash-verge.yaml;V-Ninja 的组在订阅文件里
clash_config_yaml() {
    case "$MODE" in
        v-ninja)
            local cur f
            cur=$(sed -n 's/^current:[[:space:]]*//p' "$CLASH_DIR/profiles.yaml" 2>/dev/null | head -1)
            if [ -n "$cur" ] && [ -f "$CLASH_DIR/profiles/$cur.yaml" ]; then
                echo "$CLASH_DIR/profiles/$cur.yaml"; return
            fi
            for f in "$CLASH_DIR"/profiles/*.yaml; do
                [ -f "$f" ] && grep -q '^proxy-groups:' "$f" && { echo "$f"; return; }
            done
            echo "$CLASH_DIR/config.yaml" ;;
        *) echo "$CLASH_DIR/clash-verge.yaml" ;;
    esac
}
```

后面接的 python 解析要点（完整实现见当前 `installer/安装.command` 第 1 节）：

- 定位 `^proxy-groups:` 段落，遇到顶格字母行即结束
- 以最小缩进的 `-` 作为条目分隔，**同时兼容** `- name: X` 与 `-` 换行 `name: X` 两种写法
- 只取 `type == select` 的 `name`
- 用 `python3 - "$CLASH_YAML" <<'PY_GROUPS'` 内嵌，`while read` 收集成数组 `GRPS`

# 8. 自动化脚本（升级时用这个）

脚本把第 7 节的 44 条改动变成可执行规则：

- `tools/apply_vninja.py` —— 执行器
- `tools/vninja-patch.json` —— 规则表（44 条：文件 / 旧串 / 新串 / 期望次数）

## 8.1 升级流程

```bash
# 1. 新版本是一个全新目录时，先把 tools/ 复制进去
cp -R <旧版本>/tools <新版本>/

# 2. 施加改动
python3 tools/apply_vninja.py

# 3. 确认（可反复跑，幂等）
python3 tools/apply_vninja.py --check
```

正常输出：

```
[ OK ] 1.1   core/claude-switch.sh        模式列表
[SKIP] 1.2   core/claude-switch.sh        配置目录按模式派生（已应用）
...
--------------------------------------------------------------------
成功 44 · 跳过 0 · 失败 0

语法检查：
  ✓ core/claude-switch.sh
  ✓ installer/安装.command
  ✓ daemons/claude-bodyguard.sh
```

再次运行只会输出 `[SKIP]`，不会重复改写。

## 8.2 常用参数

| 参数 | 作用 |
| --- | --- |
| （无） | 施加改动；首次改写前生成 `<文件>.vninja.bak` |
| `--check` | 只检查不写文件；有待应用项时退出码为 1 |
| `--dry-run` | 只显示将要做什么，不落盘 |
| `--revert` | 从 `.vninja.bak` 还原（每个文件还原一次） |
| `--root <目录>` | 指定仓库根目录（默认取脚本所在仓库） |

## 8.3 两种失败提示

**锚点整段找不到**（上游重写了这段代码）：

```
[FAIL] 3.5   installer/安装.command         组名来源与解析：找不到锚点（上游这段可能已重写）
...
需要人工处理：
  - [3.5] installer/安装.command 组名来源与解析：找不到锚点（上游这段可能已重写）

提示: 打开 docs/新增代理客户端适配规范.md 第 7 节，按条目编号对照改。
```

**只改了其中几处**（部分回退 / 上游结构微调）：

```
[FAIL] 1.10  core/claude-switch.sh        8 处模式判定改用 is_clash_mode：部分匹配：旧串仍有 1 处（预期 8 处），可能上游已改动
```

两种情况下脚本都会**退出码 1**，并且不继续做语法检查，避免把半成品当成功。

## 8.4 规则判定的两种类型

脚本按"新串是否包含旧串"自动分类，不需要人工标注：

| 类型 | 判定 | 例子 |
| --- | --- | --- |
| `append`（新串含旧串） | 新串出现 ≥ 预期次数即为已应用 | 在 `echo` 后追加一行、在函数前插入辅助函数 |
| `replace`（互不包含） | 必须**旧串完全消失**且新串就位才算已应用 | `pgrep -f verge-mihomo` → `clash_core_up`（7 处）、`[ "$PROXY_MODE" = "clash-verge" ]` → `is_clash_mode`（8 处） |

`replace` 类之所以要求旧串归零，是为了防止"只改了一部分"被误判成完成——这正是手工改最容易出的错。

## 8.5 注意事项

- `.vninja.bak` 只是本地保险，不要提交/打包
- 脚本只改第 7 节列出的 4 个文件，不碰文档、配置和用户数据
- 改动施加后仍然要按第 3 节做端到端验证（`check` / `checkdetail` / 保镖 `MODE`）
- 上游如果新增了与 Clash 相关的代码路径，脚本不会自动覆盖，需要人工判断是否要加 `v-ninja` 分支，并把新规则补充进 `vninja-patch.json`
- 规则按 `vninja-patch.json` 里的顺序执行，**有依赖的规则靠顺序保证**：例如 `1.6b` 先把 `pgrep -f verge-mihomo` 换成 `clash_core_up`，`1.5` 才能匹配到 `clash-verge)  clash_core_up`。新增规则时注意不要插错位置
- 施加后会生成 `<文件>.vninja.bak`，确认无误后可以删除；需要回退时先别删

# 9. 客户端侧配置：置顶规则与 DNS

> 这一节讲**运行时要生效的东西**（规则写在哪、DNS 怎么算正常），与第 7 节的"代码改动"是两回事。
> 正常情况下这些都由 `claude-switch.sh fix` 自动完成，不需要手工配；只有排障时才需要看。

## 9.1 规则由谁写、写在哪

安装器第 5 步和 `fix` 都会调用核心脚本内嵌的 Python（`clash-rules write`），把规则写进：

```
~/Library/Application Support/io.github.clash-verge-ninja.clash-verge-ninja/profiles/Script.js
```

写法是**带标记的托管块**，不覆盖用户自己的脚本：

```javascript
// >>> claude-switcher managed rules >>>
;(function () {
  const originalMain = main;
  const pinnedRules = [ ... ];
  const group = "🚀 节点选择";
  main = function (config, ...args) {
    const result = originalMain(config, ...args);
    if (!result["proxy-groups"].some((item) => item.name === group)) throw new Error("claude-switcher: configured proxy group missing");
    result.rules = pinnedRules.concat((result.rules || []).filter((rule) => !pinnedRules.includes(rule)));
    return result;
  };
})();
// <<< claude-switcher managed rules <<<
```

要点：

| 行为 | 说明 |
| --- | --- |
| 保留原脚本 | 已有的 `function main(config)` 会被包装调用，不是替换 |
| 幂等 | 重复运行只替换标记块；标记块不完整会直接报错中止 |
| 备份 | 改动前生成 `Script.js.bak.<纳秒时间戳>` |
| 组名校验 | 配置里必须存在 `PROXY_GROUP` 这个组，否则抛错（避免规则指向不存在的组） |
| 去重 | 与配置里已有规则重复的会被过滤掉 |

## 9.2 规则内容（16 条）

写入的置顶规则固定为 16 条，顺序也固定：

**前 3 条：UDP 端口**

```
AND,((NETWORK,UDP),(DST-PORT,3478)),<目标>
AND,((NETWORK,UDP),(DST-PORT,5349)),<目标>
AND,((NETWORK,UDP),(DST-PORT,19302)),<目标>
```

`<目标>` 取决于 WebRTC 策略：`proxy`（默认）→ 代理组；`reject` → `REJECT`。

**后 13 条：域名后缀 → 代理组**

```
claude.ai / claude.com / anthropic.com / claudeusercontent.com
challenges.cloudflare.com / datadoghq.com / segment.io
stripe.com / stripe.network / stripecdn.com
intercom.io / intercomcdn.com / intercomassets.com
```

这些域名全部前插到 `config.rules` 最前面，因此优先级高于订阅自带的规则。

## 9.3 切换 WebRTC 策略

默认把 STUN 流量交给代理；想直接拒绝 UDP（更严格，但可能影响通话）时：

```bash
WEBRTC_POLICY=reject ~/.local/bin/claude-switch.sh fix
```

策略会持久化到 `~/.claude-switcher/webrtc-policy`，之后的 `checkdetail`、GUI 一键修复都沿用，不需要每次传。改回代理：

```bash
WEBRTC_POLICY=proxy ~/.local/bin/claude-switch.sh fix
```

## 9.4 DNS：必须走 TUN（fake-IP）

判定方式只有一条——`claude.ai` 必须解析到 `198.18.x.x` 这个 fake-IP 网段：

```bash
dig +short claude.ai       # 期望 198.18.0.x
```

`checkdetail` 的 DNS 检查就是跑这条命令：

- 返回 `198.18.*` → `DNS=ok:走隧道`
- 返回真实 IP（如 `1.1.1.1`、`104.18.x.x`）→ `DNS=fail:未走隧道(...)`

原理：TUN 接管 `198.18.0.0/16`，客户端生成的 `config.yaml` 里通常带：

```yaml
tun:
  device: utun1024
  auto-route: true
  stack: system
  dns-hijack:
    - any:53
```

所以 **DNS 是否正常，等价于 TUN 是否真的接管了流量**。

## 9.5 TUN 前提

| 项目 | 说明 |
| --- | --- |
| 在线判定 | `ifconfig` 里出现 `inet 198.18.` 即视为 TUN 已接管（不依赖具体网卡名） |
| 开关 | 客户端配置 `verge.yaml` 的 `enable_tun_mode: true` |
| 已知坑 | 客户端更新/异常重启会把 `enable_tun_mode` 重置为 false；`fix` 会自动检测并改回来再重启客户端 |

## 9.6 怎么验证规则真的生效

不要只看配置文件，要看**运行内核加载了什么**：

```bash
# 1) 一键修复会写入并验证
~/.local/bin/claude-switch.sh fix

# 2) 自检里的规则项
~/.local/bin/claude-switch.sh checkdetail | grep 规则置顶
# 期望: 规则置顶=ok:已验证内核加载

# 3) 直接查内核（secret 见 config.yaml）
curl -s -H "Authorization: Bearer <secret>" http://127.0.0.1:9097/rules \
  | python3 -c "import sys,json;[print(i+1,x['payload'],'->',x['proxy']) for i,x in enumerate(json.load(sys.stdin)['rules'][:5])]"
```

期望前 5 条：3 条 UDP → `REJECT`（或代理组），紧接着 `claude.ai` / `claude.com` → 你的代理组。

`verify_runtime()` 会逐条比对前 16 条的**类型、payload、目标组、是否被禁用**，任何一条不符都会报 "运行规则未按策略置顶:<规则>"。

## 9.7 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `规则置顶=fail:未生效` | `Script.js` 没被客户端加载（全局扩展脚本未启用） | 客户端里确认「全局扩展脚本」开启，重启客户端后重跑 `fix` |
| `运行规则未按策略置顶:claude.ai` | 旧版把规则写进了 profile 级 `prepend`，排在 `Script.js` 之前 | `grep -rl "intercomassets.com" profiles/` 找到并清空（先备份），重启客户端 |
| `DNS=fail:未走隧道(1.1.1.1)` | 没开 TUN 或 fake-IP | 打开 TUN + fake-IP，确认 `dig claude.ai` 返回 198.18.x |
| UDP 规则指向 `REJECT` 但想走代理 | 之前设过 `reject` 策略并持久化了 | `WEBRTC_POLICY=proxy claude-switch.sh fix` |
| 全局模式（`mode=global`）下规则"不生效" | 全局模式不走规则匹配，全部流量直接走代理 | 属正常：自检显示 `规则置顶=ok:全局模式(全部流量走代理)` |
| 组名改了之后规则报错 | `Script.js` 里还记着旧组名 | 重跑 `fix`（会按当前 `PROXY_GROUP` 重写并校验） |

## 9.8 和"客户端手动配置"的边界

- **由本工具负责**：`Script.js` 里的 16 条置顶规则、WebRTC 策略、TUN 开关自愈、时区/IPv6/DNS 缓存
- **由客户端负责**：节点选择、订阅更新、代理组结构、fake-IP 开关、端口
- **需要人工处理**：订阅自带规则与置顶规则冲突、上游客户端大版本改了脚本扩展机制
